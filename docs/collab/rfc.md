# RFC: совместное редактирование DOCX в WordCraft

- Статус: Draft (реализация — `STATUS.md`, PR #5834)
- Автор: `wordcraft/envoy`
- ADR: `../.craft/bus/decisions/0001…0010` (Phase 0 закрыт, 10/10 accepted)
- Upstream issue/PR: PR в `storytold/wordcraft`, ветка `feature/realtime-collaboration`
- Основание: `study.md`, `options.md` (этот каталог), `TASK.md`, `INTEGRATION.md`

## 1. Контекст

WordCraft — однопользовательский редактор: одна `Session`, один автор, undo — глобальные
снапшоты `Document` (`engine/src/session/history.rs:7`), сети в кодовой базе нет вовсе.
Модель — дерево историй (`body` + `parts`), абзацев (`String` + `Vec<Run{len, props}>`),
таблиц и inline-объектов; стабильных ID узлов нет, позиция — `Pos { story, path, off }`
(`doc/src/position.rs:15,60`). Мутация — `Session::run(id, &Value)`, 656 команд, команды
относительны выделения (`engine/src/session/run.rs:55`).

Phase 0 зафиксировал: единица операции — нормализованная intent-операция, исполняемая
сервером (ADR-0001), session-scoped ID (ADR-0002), серверный `version` + `opId`-дедуп
(ADR-0003), классы `merge`/`structural` (ADR-0004), снапшот + журнал (ADR-0005),
presence в общем WS (ADR-0006), один control plane + per-app адаптер (ADR-0007), JWT +
lease (ADR-0008), commit сервером (ADR-0009), per-user undo (ADR-0010).

## 2. Цели и не-цели

Цели (из `TASK.md`):
1. 2–5 участников правят один `.docx` в реальном времени; курсоры, выделения, участники.
2. Порядок, версии, идемпотентность, догон после reconnect.
3. Per-user undo/redo; чужие правки не откатываются.
4. Роли `owner/editor/commenter/viewer` проверяются сервером.
5. Commit сервером; `.docx` не ломается, немоделируемое сохраняется как раньше.
6. Фича за флагом; одиночный режим — по умолчанию.

Не-цели: аккаунты/облако/биллинг, несколько документов в одной сессии, офлайн-правка
(в v1 только догон), мобильный UX, полная совместимость с Word.

## 3. Модель данных для синхронизации

### 3.1. Единица операции (ADR-0001)

```json
{"opId":"c7:12","docId":"...","actorId":"sub","baseVersion":41,"epoch":7,
 "kind":"primitive|command|structural|merge",
 "target":{"story":"body","nodeId":18,"off":42},
 "payload":{"text":"Привет"},
 "history":{"action":"undo","opId":{"client":"c7","seq":11}}}
```

- `kind:"primitive"` — позиционная операция над моделью: `insert_text`, `delete_range`,
  `split_para`, `merge_para`, `set_run_props`, `set_para_props`, `insert_block`,
  `remove_block`, `move_block`, `permute`, `set_para_level`, `set_para_list`,
  `set_para_multilevel`, `set_para_restart_numbering`, `insert_row`, `remove_row`,
  `insert_column`,
  `remove_column`, `merge_cells`, `split_cells`, `set_style`, `add_comment`,
  `resolve_comment`, `set_field`. `split_cells`, `merge_cells` и `insert_column`
  несут необязательное поле `restore` — данные обратной операции (§6, §10).
- `kind:"command"` — нормализованная команда движка с явным адресом и контекстом:
  `payload: {"command":"format.bold","params":{...},"pending":<CharProps>}`; каретка
  берётся из `target`, `pending` — из payload, `author` — из JWT `sub` (сервер
  подставляет его в `Session`). Команда исполняется тем же `Session::run`, что и в UI.
  Допустимы только команды, меняющие документ, и только вне запрещённых областей
  (`file.`, `tools.`, `ui.`, `view.`, `caret.`, `select.`, `collab.`, `edit.undo`,
  `edit.redo`, `edit.repeat`, `review.readAloud`); остальные — `forbidden`.
- `kind:"structural"` — эксклюзивно, `baseVersion == head`: вставка/удаление таблицы,
  `parts`, смена стиля/нумерации, paste фрагмента.
- `kind:"merge"` — комментарии и свойства, не зависящие от структуры (LWW по свойству).

Клиент выводит примитивы из своей локальной команды: `Arc::ptr_eq` по `body`/`parts`
даёт изменённые блоки бесплатно, внутри изменённого абзаца — минимальный текстовый дифф
по байтовым смещениям. Сырые `Session::run(id, params)` на проводе запрещены.

`kind:"command"` — запасной путь для команд, чей эффект клиент не смог нормализовать в
примитивы. Авторитетная дельта такой операции повторяет саму операцию
(`{"op":"command","command","params","nodeId","off","pending"}`), чтобы остальные
реплики исполнили её локально при том же документе.

Обратной операции у произвольной команды нет: команда не replay-абельна назад
(toggle переключится ещё раз, `growFont` сдвинет size дважды). Поэтому шаг
`kind:"command"` записывается без `inverse` и служит **барьером** (ADR-0010):
undo на нём отвечает `unsupported`, а не перескакивает к более старому шагу.
Исключение — частые команды форматирования: для них сервер собирает точную
обратную операцию-примитив `set_para_format` из значений **до** команды
(см. §6).

**Границы с движком.** Производное (layout, номера страниц, результаты полей, метки
списков) не пересылается — пересчитывается каждой репликой (`Session::layout()`).
`kept`/`passthrough` не пересылаются и живут на авторитетной копии (см. §4.6).

### 3.2. Идентификаторы (ADR-0002)

- Сервер при join строит карту `nodeId ↔ (story, path)` для абзацев, таблиц, их строк и
  ячеек (а также абзацев внутри ячеек) и выдаёт
  `partId`/`commentId`/`revisionId` из **серверных диапазонов** вместо локального
  `free_id()` (`doc/src/parts.rs:8`). Путь — это `doc::Path`: `[block]` — блок стори,
  `[block, row]` — строка таблицы, `[block, row, cell]` — ячейка,
  `[block, row, cell, block]` — абзац в ячейке.
- Операции адресуют `(nodeId, off)`; индекс-путь — только внутри `nodeId`.
- Структурная правка сдвигает индекс в **своём** контейнере
  (`insert_block`/`split_para` — блоки стори, `insert_row`/`remove_row` — строки
  таблицы, `insert_column`/`remove_column`/`split_cells` — ячейки строки, которая
  получила или потеряла ячейку): id ячейки переезжает вместе с содержимым, id
  соседних ячеек не меняется. Ячейку, расширившуюся над вставленным или удалённым
  столбцом, никуда не сдвигает. `merge_cells` оставляет id первой ячейки диапазона и
  уносит в надгробия поглощённые. Удалённый блок/строка/ячейка уносит id поддерева
  в надгробия.
- Удалённые `nodeId` попадают в надгробия на окно журнала; операция по ним —
  `rejected{code:"gone", retryable:false}`. Обратная операция, которая возвращает
  содержимое узла (undo слияния, удаления столбца), возвращает и его id: держатель
  каретки снова адресует свою ячейку.
- Ревизии track changes адресуются **индексом** в `Document::revisions`
  (`CharProps.ins/del`, `doc/src/props/char_props.rs:353`). При вставке/удалении ревизии
  сервер перенумеровывает ссылки и рассылает `primitive` `remap_revisions` — это часть
  операции, а не отдельный протокол.
- `media`-ключи — строки; сервер префиксует их `clientId`, чтобы два клиента не записали
  один ключ.

### 3.3. Документ на сервере

`Room = (docId)` хранит: `Document` (авторитетная модель), `version`, `epoch`,
журнал `Vec<JournalEntry>` с `opId`-окном, карту ID, надгробия, базовый `.docx` (для
`kept`/`passthrough`) и per-user стеки undo. Снапшот — §4.6.

## 4. Протокол

### 4.1. Транспорт

WebSocket, JSON text frames (UTF-8), один фрейм ≤ 1 MiB; TLS снаружи (reverse proxy).
`ping/pong` на уровне WS + heartbeat раз в 15 с. Отсутствие heartbeat 45 с → разрыв.
Бинарные фреймы зарезервированы под чанки снапшота.

### 4.2. Сообщения

| Тип | Направление | Поля | Семантика |
|---|---|---|---|
| `auth` | C→S | `token`, `client_id`, `last_version?` | первое сообщение; токен не в URL |
| `welcome` | S→C | `session_id`, `role`, `participants`, `version`, `epoch`, `snapshot?` | вход в комнату |
| `op` | C→S | `opId`, `baseVersion`, `epoch?`, `kind`, `target`, `payload` | операция |
| `applied` | S→C | `opId`, `version`, `epoch`, `delta`\|`state` | авторитетный результат |
| `rejected` | S→C | `opId`, `code`, `retryable`, `details?` | отказ |
| `presence` | C→S | `cursor`, `selection`, `viewport`, `active` | не журналируется |
| `presence` | S→C | `client_id`, `role`, `state` | `role` ставит сервер из JWT, не клиент |
| `snapshot` | S→C | `version`, `chunk`, `last` | догон/ресинк |
| `commit` | C→S | `op_id`, `expected_version`, `etag?` | сборка файла |
| `committed` | S→C | `version`, `sha256`, `bytes?`, `warnings[]` | результат |
| `error` | S→C | `code`, `message`, `retryable` | вне операций |
| `ping`/`pong` | C↔S | `ts` | heartbeat |

Коды отказа: `stale` (retryable), `conflict`, `forbidden`, `gone`, `lease`,
`token-expired` (retryable), `too-large`, `invalid`.

**Примитив `move_block`.** Перемещение соседних блоков (`para.moveUp`/`moveDown`
и клиентский diff, §6) — структурная операция с двумя явными адресами:
`target.nodeId` — первый блок перемещаемого отрезка, `payload.count` — длина
отрезка (1…64), `payload.neighbour` — блок, рядом с которым стоит отрезок.
Отрезок и сосед меняются местами; авторитетная дельта повторяет операцию с id
отрезка: `{"op":"move_block","nodeId":42,"count":1,"neighbour":17}`. Все id ниже
контейнера переезжают вместе со своими блоками (`NodeIds::permute_children`),
поэтому владелец каретки в перемещённом абзаце (в том числе в таблице) её
сохраняет. Неизвестный id — `invalid`, отозванный — `gone`, сосед из другого
контейнера или не рядом с отрезком, таблица на пути, отрезок с разрывом секции
или выход за контейнер — `invalid`; всё это проверяется до мутации, документ и
`version` не меняются. Операция обратна сама себе: сосед проходит отрезок по
одному блоку, поэтому undo отрезка длиной `n` — это `n` операций в одной дельте
`transaction`. Отрезок шире 64 блоков не нормализуется и остаётся командой,
undo на нём отвечает `unsupported`.

**Примитив `permute`.** Сортировка отрезка абзацев (`para.sort`, а также
любая перестановка, которую diff клиента узнаёт по указателям `Arc`) —
структурная операция с явным списком id в новом порядке:
`payload: {"op":"permute","nodeId":<первый id нового порядка>,"order":[id…]}`.
Id обязаны принадлежать одному контейнеру и вместе заполнять один
непрерывный отрезок не длиннее 64 абзацев. Дубликат id, неизвестный id
(`invalid`), отозванный id (`gone`), id из другого контейнера или список с
пропуском между индексами, таблица внутри отрезка и выход за контейнер
отклоняются до мутации: документ и `version` не меняются. Все id ниже
контейнера переезжают вместе со своими блоками
(`NodeIds::permute_children`), поэтому каретка в отсортированном абзаце
сохраняет id. Авторитетная дельта — операция в одной транзакции шага:

```json
{"op":"transaction","ops":[{"op":"permute","nodeId":42,"order":[42,17,9]}]}
```

Обратная операция — тот же `permute` со старым порядком id; благодаря
транзакции и forward, и undo приходят на реплики одной дельтой. Шаг
сообщает в `touched` все блоки отрезка с поддеревьями. Сортировка шире 64
блоков не нормализуется: команда исполняется, шаг остаётся командой, undo
отвечает `unsupported`.

**Примитив `set_para_level`.** Promote/demote (`para.promote`/`para.demote`,
`outline.promote`/`demote`, а также абсолютные уровни вкладки Outlining) —
структурная операция, которая называет целевой уровень каждого абзаца явно:

```json
{"op":"set_para_level","items":[{"id":42,"level":2},{"id":17,"level":null}]}
```

`level: 1…9` даёт абзацу `Heading{n}`, `level: null` — основной текст; блоки и
порядок не меняются, поэтому карта id остаётся как была. Необязательные
`style` и `outline` называют точный стиль и прямой outline level — так
обратная операция возвращает абзац, чей прежний стиль уровень не подразумевает
(`Quote`, `Heading2` при прямом outline level 0); `outline` без `style`
отклоняется, потому что подразумеваемый стиль всегда чистит прямой уровень.
Неизвестный id — `invalid`, отозванный — `gone`, id таблицы/строки/ячейки или
абзаца, вышедшего за свой контейнер, — `invalid`; дубликат id и список длиннее
64 абзацев — `invalid`. Всё проверяется до мутации: документ и `version` не
меняются. Авторитетная дельта — операция в одной транзакции шага (если команда
меняет ещё и порядок, рядом кладётся `permute`):

```json
{"op":"transaction","ops":[{"op":"set_para_level","items":[{"id":42,"level":2}]}]}
```

Обратная операция называет прежние уровни тех же id, поэтому undo и redo
приходят на реплики одной дельтой. Шаг сообщает в `touched` каждый абзац,
чей уровень изменился: чужая правка в любом из них после шага — `undo-conflict`
без изменения документа и без движения версии. Promote/demote шире 64 абзацев
и выделение с элементом списка (команда меняет ещё и уровень списка, а не
только заголовка) не нормализуются: шаг остаётся командой, undo отвечает
`unsupported`. Шаг, который называет те же уровни, что уже стоят, всё равно
адресуем: документ не меняется, дельта и обратная операция есть.

**Примитив `set_para_list`.** Bullets и Numbering (`para.bullets`/`para.numbering`)
— структурная операция, которая делает список адресуемым: целевые абзацы
задаются списком id, вид (`bullets`/`numbering`) и уровень (`0…8`) — явно:

```json
{"op":"set_para_list","ids":[42,17],"kind":"bullets","level":1}
```

Определение нумерации выбирается или создаётся детерминированно: сначала
ищется существующий список, чьи девять уровней совпадают с каноническими для
вида, иначе вызывается тот же `free_id`-аллокатор, что и в `para.bullets`.
Функция — чистая от документа, поэтому одинаковый payload на одинаковом
документе даёт одинаковый abstract id и `num`; redo после undo переиспользует
определение первого прохода, а не создаёт второе. Абзац, который уже стоит в
списке этого вида на этом уровне, не трогается (ни стиль, ни отступы), поэтому
повторный шаг — identity: дельта есть, документ не меняется, новое определение
не создаётся.

Точная форма (её пишут путь команды и обратная операция) называет полное
list-состояние каждого абзаца — `num` (или `null` — наследовать, `0` — вне
списка), `level`, `style` и четыре отступа, которые чистит команда, — и
определения, которые шаг добавляет:

```json
{"op":"set_para_list",
 "items":[{"id":42,"num":3,"level":1,"style":"ListParagraph",
           "indentLeft":null,"indentFirst":null,
           "indentLeftChars":null,"indentFirstChars":null}],
 "define":[{"abstract":{…},"num":{…}}]}
```

Реплика, которая не исполняла команду, создаёт определение из `define` с теми
же id и уровнями, поэтому обе реплики держат один и тот же JSON документа
вместе с numbering-таблицей. Коллизия с существующим определением (тот же id,
другое тело) и `num`, которого нет ни в документе, ни в шаге, отклоняются.
Неизвестный id — `invalid`, отозванный — `gone`, таблица/строка/ячейка/абзац
внутри таблицы (операция адресует только абзацы верхнего уровня), дубликат,
пустой набор, уровень вне `0…8`, неизвестный вид и шаг шире 64 абзацев —
`invalid`; всё проверяется до мутации, документ и `version` не меняются.
Авторитетная дельта — операция в одной транзакции шага:

```json
{"op":"transaction","ops":[{"op":"set_para_list","items":[…],"define":[…]}]}
```

Обратная операция — точный `set_para_list` с прежним состоянием и `undefine`
созданного `num`; определение удаляется, только если на него больше не
ссылается ни абзац, ни стиль, ни другой список, поэтому чужая правка сохраняет
метку. Прежние ссылки на списки возвращаются, а поскольку определение
удаляется, redo создаёт его снова с тем же id и приходит к тому же JSON.
Шаг сообщает в `touched` каждый абзац, чей list-состояние изменилось: чужая
правка в любом из них после шага — `undo-conflict` без изменения документа, без
движения версии и с сохранением шага на стеке.

**`set_para_multilevel`.** Multilevel List (`para.multilevel`) — та же
структурная операция для девятиуровневого списка: каждый абзац задаётся парой
(id, уровень `0…8`), вид — `legal` (`1.`, `1.1.`, `1.1.1.`) или `outline`:

```json
{"op":"set_para_multilevel","kind":"legal",
 "levels":[{"id":42,"level":0},{"id":17,"level":2}]}
```

Определение выбирается или создаётся тем же детерминированным правилом, что и
у `set_para_list` (канонические девять уровней вида, иначе `free_id`), поэтому
одинаковый payload на одинаковом документе даёт тот же `num` на обеих
репликах. Абзац, который уже стоит в этом определении на своём уровне, не
трогается: повтор шага — identity, документ не меняется и новое определение не
аллоцируется. Точная форма — общая (`items`, `define`, `undefine`) под именем
`set_para_multilevel`; обратная операция — точная операция с прежним
состоянием и `undefine` созданного определения. Уровень вне `0…8`,
неизвестный вид, дубликат, пустой набор, таблица и абзац внутри неё, шаг шире
64 абзацев отклоняются до мутации; неизвестный id — `invalid`, отозванный —
`gone`.

**`set_para_restart_numbering`.** Restart numbering (`para.restartNumbering`)
— отдельная структурная операция с явным стартом:

```json
{"op":"set_para_restart_numbering","ids":[42,17],"start":3}
```

Все адресованные абзацы должны уже стоять в одном списке — restart
перезапускает один список. Адаптер создаёт новый `num` тем же аллокатором
документа и копирует abstract и level overrides источника, затем ставит
`startOverrides = [(уровень, start)]` для каждого использованного уровня;
аллокация — чистая функция документа, поэтому обе реплики выбирают один id.
Если адресованные абзацы уже сидят в экземпляре с ровно такими overrides, шаг
— identity: документ не меняется, второй экземпляр не создаётся. `start`
принимается в `1…=100_000` (граница команды «Set Numbering Value»); 0,
отрицательное значение, пустой набор, абзац вне списка, restart двух разных
списков, дубликат, таблица и шаг шире 64 абзацев отклоняются до мутации.
Точная форма — общая (`items` с полным list-состоянием, `define` нового
экземпляра, `undefine`), под именем `set_para_restart_numbering`; undo
возвращает прежние ссылки и снимает созданный экземпляр, redo создаёт его
снова с тем же id.

### 4.3. Порядок и версии (ADR-0003)

- `version: u64` на документ, +1 на принятую операцию; `epoch` — на structural-операцию.
- `opId = (clientId, seq)`; сервер хранит окно ≥ 24 ч / ≥ 10 000 операций и на повтор
  возвращает сохранённый `applied`, **не исполняя** операцию заново (undo, relative
  moves и вставки неидемпотентны). Окно переживает восстановление из снапшота (§4.6).
- `baseVersion` — контекст, не блокировка; для `structural` — строго `baseVersion == head`.
- Presence не увеличивает `version`.

### 4.4. Конфликты (ADR-0004)

| Ситуация | Политика | Что видит пользователь |
|---|---|---|
| Двое печатают в одном абзаце | серверный порядок, `insert_text` со сдвигом `off` | текст обоих, каретка не прыгает |
| Правка в удалённом абзаце | `rejected{code:"gone"}` | «абзац удалён», курсор на соседний |
| Structural против structural | очередь, второй ждёт `head` | индикатор «синхронизация…» |
| Смена стиля/нумерации | `structural`, эксклюзивно | краткая блокировка, затем пересчёт |
| Перемещение соседних абзацев | `structural move_block` по двум id, отрезок ≤ 64 | порядок одинаков у всех; undo/redo двигает обратно |
| Сортировка абзацев | `structural permute` по списку id, отрезок ≤ 64 | порядок одинаков у всех; undo/redo возвращает прежний порядок одной транзакцией |
| Promote/demote абзацев | `structural set_para_level` по списку (id, уровень) | уровни одинаковы у всех; undo/redo возвращает прежние уровни и стили одной транзакцией |
| Bullets/Numbering | `structural set_para_list` по списку id, виду и уровню; определение нумерации детерминировано | списки одинаковы у всех; undo/redo возвращает прежние уровни и numbering id одной транзакцией |
| Multilevel List | `structural set_para_multilevel` по списку (id, уровень 0…8) и виду (`legal`/`outline`); девятиуровневое определение детерминировано | уровни одинаковы у всех; повтор — identity; undo/redo возвращает прежние уровни и numbering id одной транзакцией |
| Restart numbering | `structural set_para_restart_numbering` по списку id и явному `start`; новый экземпляр списка детерминирован | перезапуск одинаков у всех; повтор — identity; undo/redo возвращает прежний экземпляр одной транзакцией |
| Комментарий к удалённому якорю | `rejected` или перенос к ближайшему узлу по ADR-0004 | бейдж «комментарий потерял якорь» |
| Устаревшая база | `applied` с `conflict:true` + дельта | слияние без диалога |

OT/CRDT не используются: сервер применяет операцию к head и возвращает результат.

### 4.5. Reconnect и догон

1. `auth{last_version}` → если версия в журнале: `welcome` + хвост `applied` по порядку.
2. Если версия вытеснена: `welcome` + `snapshot` (чанки) + `version`; клиент заменяет
   модель и сбрасывает непринятую очередь.
3. Непринятые операции клиент хранит с `opId` и переигрывает после `welcome`; повторный
   `opId` дедуплицируется сервером.

### 4.6. Снапшоты и compaction (ADR-0005)

- Снапшот сессии = **модель JSON** (`serde` `Document`) **плюс исходные байты `.docx`**,
  из которых она открыта. Причина: `Document::kept` помечен `#[serde(skip)]` и в JSON не
  попадает (`doc/src/lib.rs`), а без `kept` commit теряет немоделируемый XML правленых
  абзацев. Байты `.docx` дают `kept`/`passthrough` при восстановлении.
- Вместе с ними хранится **окно `opId`** — сохранённые `applied`-ответы до версии
  снапшота (`dedup.json`, oldest first). Это состояние сервера, на провод оно не
  выходит: повтор после рестарта — обычная `op` с тем же `opId`, ответ — сохранённый
  `applied`, `version` не двигается. Окно обрезается до версии снапшота и до лимита
  10 000, вытесняя старейшие; снапшот без `dedup.json` открывается с пустым окном.
- Хранится 2 снапшота; журнал обрезается по версии снапшота; восстановление = снапшот +
  реплей хвоста.
- Частота: 500 операций / 5 минут / перед подключением нового участника при длинном
  журнале. Commit — отдельная операция и отдельный формат (`.docx`), падение writer'а не
  ломает сессию.

> **Расхождение с ADR-0005.** ADR-0005 (строка про wordcraft) говорит «модель/`kept`/
> `passthrough`». Это неверно для `kept` (`#[serde(skip)]`). Реализация следует факту;
> прошу chair выпустить уточняющий ADR (supersedes) до merge.

## 5. Presence (ADR-0006)

Эфемерный тип в том же WS: `{cursor:{story,nodeId,off}, selection?, viewport:{page,scroll},
active:{tab,pane}}`. 5–10 Гц, ≤ 2 KiB, коалесцирование в последнее состояние,
`drop-stale` при перегрузке, TTL 30 с, `leave`/разрыв чистит сразу. Не журналируется,
не влияет на `version`; автору своё состояние не эхо-броадкастится. viewer шлёт presence.
Сервер добавляет в броадкаст `role` из JWT (ADR-0008), чтобы пир, подключённый
раньше, видел роль нового участника с первого же кадра.

## 6. Undo/redo на пользователя (ADR-0010)

- Сервер ведёт per-user стек шагов: `{actorId, label, version, inverse[], forward[], touched[]}`;
  шаг = операции одного пользовательского действия.
- Запрос — **новая операция** с полем `history`: `{"action":"undo","opId":<id шага>}`
  или `{"action":"redo",...}`. Отдельного сообщения `undo` в конверте нет: так undo
  проходит те же проверки роли, `opId`-дедупа и `baseVersion`, что и правка, и получает
  ровно один `version`. Обратные операции шага исполняются под этой операцией и
  отдельно не журналируются.
- `opId` в `history` — id операции, создавшей шаг. Сервер берёт только **новейший**
  шаг актора; старый id (устаревшее меню) → `undo-conflict`.
- Подтверждённый ответ на `history` несёт то же действие в `Applied.history`
  (serde-default, поэтому окно дедупа и старые снапшоты читаются). Обычный ответ
  на свою правку клиент не применяет — она уже применена оптимистично; ответ на
  `history` применяется: обратной копии у автора нет, движок для undo не
  запускался, поэтому дельта автора — единственная и должна лечь ровно один раз.
  Это один путь для текста и для структурных инверсий (merge/split/remove_column).
- Отказ undo (`undo-conflict`, `unsupported`) не ломает сессию: документ не менялся,
  шаг остаётся на стеке, а сообщение показывается автору; `stale`, `gone`, lease и
  истёкший токен переводят сессию в resync.
- Конфликт: если после шага другая операция трогала тот же `nodeId` (primitive) или
  документ пережил structural-операцию (structural-шаг) — `undo-conflict`, ничего не
  меняется. Операция также сообщает узлы помимо своей цели, содержимое которых
  перезапишет её обратная (`Effect::touched`): ячейки слияния, ячейка и её части при
  разбиении, ячейки вставленного столбца, вставленный блок/строка. Правка другого
  пользователя в одном из них после шага — тоже `undo-conflict`, а не молчаливая
  потеря его текста; правка в ячейке, которую шаг не трогал, undo не блокирует.
  Молчаливой перезаписи нет.
- Шаг из нескольких операций исполняется транзакцией: все обратные операции
  применяются под одной версией, и если одна отказывает, уже применённые
  откатываются — документ не остаётся между состояниями. Реплики получают шаг
  одной дельтой `{"op":"transaction","ops":[…]}` и применяют её на копии
  документа и карты узлов: либо всё, либо ничего.
- `kind:"command"` не имеет обратной операции, поэтому он — **барьер**: шаг
  записывается без `inverse`, undo на нём отвечает `unsupported` и не перескакивает к
  более старому шагу. Исключение — команды из списков
  `CHAR_FORMAT_COMMANDS`/`PARA_FORMAT_COMMANDS` в `collab-engine`: они получают
  точную обратную операцию. У команд, меняющих только свойства (runs, mark,
  `ParaProps`), обратная операция несёт эти поля; у `format.changeCase` и
  `format.enclose`, которые переписывают сами символы, она несёт ещё текст
  абзаца и его inline-объекты (oписание ниже).
- **Инверсия форматной команды — примитив `set_para_format`.** Перед запуском
  команды сервер снимает каждый абзац, который она может затронуть (выделение,
  слово под каретой, mark пустого абзаца): это абзацы между концами выделения.
  Снимок — текст, inline-объекты, runs, mark и `ParaProps`. После запуска
  сервер сравнивает и на каждый изменившийся абзац выдаёт
  `{"op":"set_para_format",…}` — только изменившиеся поля, значениями **до**
  команды. Если команда переписала символы (`format.changeCase`,
  `format.enclose`), обратная операция несёт `text` (прежний текст), `objects`
  (прежние inline-объекты, в том числе поле `EQ \o`), `runs` того текста и
  `expect` — текст, который абзац держит **после** команды, чтобы устаревшая
  инверсия не легла поверх чужой правки. Прямой эффект по-прежнему едет как
  `command` и повторяется репликами; обратный — как примитив, поэтому toggle и
  относительные шаги (`growFont`) отменяются точно, а смена регистра
  возвращает и текст, и раскладку ранов в исходном виде. Несколько абзацев
  дают несколько обратных операций и одну дельту `transaction`, как у таблиц;
  автор и пир применяют её как один и тот же JSON. Redo, как и раньше,
  повторяет исходную команду: после точного undo состояние равно состоянию до
  неё, поэтому toggle вычисляется в то же значение.
- **Адресуемость проверяется до мутации.** Если абзац из выделения не имеет
  session id (обратная операция не смогла бы его назвать), команда отклоняется
  до запуска. Сам примитив принимает только узел-абзац (таблица, строка,
  ячейка, неизвестный/удалённый узел — `invalid`; id, который комната уже
  отозвала, — `gone`). Список ранов обязан байт-в-байт покрывать целевой текст
  и заканчиваться на границах символов; у восстановления тела `expect` обязан
  совпадать с текущим текстом, а число inline-объектов — с числом символов
  `U+FFFC` в этом тексте; иначе отказ до записи. Никакой нормализации «как
  получится».
- **Чужая правка тех же полей — `undo-conflict`.** Шаг сообщает в `touched` все
  затронутые абзацы. Любая операция другого пользователя (текст или другое
  форматирование) в таком абзаце после шага делает undo конфликтом: обратная
  операция перезаписала бы чужие значения, поэтому документ не меняется
  вообще, а шаг остаётся на стеке. Правка в абзаце, который шаг не трогал, undo
  не блокирует.
- **Инверсия перемещения блоков — `move_block`.** На пути команды
  `para.moveUp`/`moveDown` (и `outline.moveUp`/`moveDown`), а также в diff
  клиента перемещение соседних блоков становится структурной операцией с двумя
  id (§4.2): id первого блока отрезка и id соседа, отрезок ≤ 64 блоков.
  Обратная операция — сосед проходит отрезок по одному блоку; для отрезка
  длиннее одного это несколько операций под одной версией, и реплики получают
  одну дельту `transaction`. Шаг сообщает в `touched` все блоки отрезка и
  соседа с поддеревьями: чужая правка в любом из них после шага — `undo-conflict`
  без изменения документа и без движения версии, шаг остаётся на стеке. Шаг
  шире 64 блоков не нормализуется и остаётся барьером.
- **Инверсия сортировки — `permute`.** `para.sort` (и перестановка, которую
  diff клиента узнаёт по `Arc`) становится структурной операцией с явным
  списком id в новом порядке (§4.2). Обратная операция — тот же `permute` со
  старым порядком; и forward, и undo приходят одной дельтой `transaction`.
  `touched` содержит все блоки отрезка, поэтому чужая правка в любом из них
  после шага — `undo-conflict` без изменения документа и без движения версии.
  Сортировка шире 64 блоков не нормализуется и остаётся барьером.
- **Инверсия promote/demote — `set_para_level`.** На пути команды
  `para.promote`/`demote` (и уровней Outlining) сервер сравнивает документ до и
  после команды и, если изменились только стиль и прямой outline level не
  более 64 абзацев, отдаёт шаг как `set_para_level` со списком (id, уровень)
  (§4.2). Обратная операция называет прежние уровни, а где уровень их не
  подразумевает — и точный стиль/`outline`; и forward, и undo приходят одной
  дельтой `transaction`, поэтому автор и пир видят один и тот же JSON.
  `touched` содержит каждый абзац, чей уровень изменил шаг: чужая правка в
  любом из них после шага — `undo-conflict` без изменения документа и без
  движения версии, шаг остаётся на стеке. Команда, которая меняет ещё и
  уровень списка или порядок блоков, и шаг шире 64 абзацев остаются барьером.
- **Инверсия списков — `set_para_list`.** На пути команды
  `para.bullets`/`para.numbering` сервер сравнивает документ до и после: если
  изменилось только list-состояние не более 64 абзацев (номер списка, стиль и
  четыре отступа, которые чистит команда), шаг отдаётся как `set_para_list` с
  точным состоянием каждого абзаца и определением нумерации, которое команда
  создала (§4.2). Обратная операция называет прежние ссылки на списки и
  `undefine` созданного `num` (определение снимается, только пока на него никто
  не ссылается); и forward, и undo приходят одной дельтой `transaction`,
  поэтому автор и пир видят один и тот же JSON, а redo создаёт то же
  определение с тем же id. `touched` содержит каждый абзац, чьё list-состояние
  изменил шаг: чужая правка в любом из них после шага — `undo-conflict` без
  изменения документа и без движения версии, шаг остаётся на стеке. Команда,
  которая меняет ещё и текст, порядок блоков или существующее определение,
  абзац внутри таблицы, абзац без session id и шаг шире 64 абзацев остаются
  барьером.
- **Инверсия multilevel и restart — свои операции того же шаблона.**
  `para.multilevel` и `para.restartNumbering` проходят тот же дифф документа:
  если изменилось только list-состояние не более 64 абзацев, шаг отдаётся как
  `set_para_multilevel` (уровни каждого абзаца и девятиуровневое определение)
  или `set_para_restart_numbering` (новый экземпляр с явными
  `startOverrides`) (§4.2). Обратная операция называет прежнее состояние и
  `undefine` созданного определения; forward и undo приходят одной дельтой
  `transaction`, redo создаёт определение/экземпляр с тем же id. `touched`
  содержит каждый затронутый абзац: чужая правка в любом из них после шага —
  `undo-conflict` без изменения документа и без движения версии. Команда,
  которая меняет ещё и текст, порядок блоков или существующее определение,
  абзац внутри таблицы, абзац без session id и шаг шире 64 абзацев остаются
  барьером.
- **Границы среза.** В списках команды `format.*` (символ, включая
  `changeCase`/`enclose`) и `para.*` (абзац: выравнивание, отступы, интервалы,
  keep, табуляции, границы, заливка, направление, стиль). Барьерами остаются
  перемещение и сортировка шире 64 блоков, promote/demote, multilevel и
  restart шире 64 абзацев, `para.removeBlank` и прочие команды, не выразимые
  снимком абзаца.
  Выделение шире 256 абзацев не снимается: шаг записывается без `inverse` и
  undo отвечает `unsupported`, а не отправляет неограниченную транзакцию.
- Redo симметрично; после undo шаг сохраняет версию undo, поэтому redo разрешён, пока
  никто не тронул цель снова. Чужие операции не откатываются; лимит 200 шагов на
  пользователя, TTL сессии.
- Локальный undo-стек `Session` не участвует: применение чужих операций и undo идут
  отдельным путём, мимо `checkpoint()` (`engine/src/session/history.rs:7`).

## 7. Роли и права (ADR-0008)

JWT первым сообщением: claims `{sub, aud, doc, app, role, sid, iat, exp, ver}`,
асимметричная подпись (ES256). Роль проверяется на каждой операции:

| Роль | Presence | Snapshot | Op | Commit |
|---|---|---|---|---|
| owner | да | да | да | да |
| editor | да | да | да | нет |
| commenter | да | да | только `add_comment`/`resolve_comment` | нет |
| viewer | да | да | `forbidden` | нет |

`author` операции подставляет сервер из `sub` — клиентский `author` не принимается.
Lease — одна комната на файл, TTL + heartbeat; отзыв закрывает WS по `sid`.

## 8. Commit и версии (ADR-0009)

- `commit{op_id, expected_version, etag}` → сервер собирает `.docx` из авторитетной модели
  `io::save_bytes` (`engine/src/io.rs:441`) и отдаёт кабинету байты + `sha256` + `version`.
- `expected_version`/`etag` не совпал с текущим файлом → `409`; предложение «сохранить
  копию».
- Ответ несёт `warnings[]`: что именно не сохранится (правленые абзацы, чей `kept`
  выброшен; неизвестные части, если `passthrough` не было). Пустой `warnings[]` —
  round-trip без потерь по модели.
- Идемпотентность: повтор с тем же `opId`/версией возвращает тот же результат.
- Кабинет создаёт новую версию, предыдущая сохраняется (его ответственность).

## 9. Сервер

- `crates/collab` — протокол, состояние комнаты, журнал, дедуп, ID-карта, undo,
  транспортно-независимо (тестируется без сети).
- `crates/collab-doc` — адаптер модели `Document` к позиционным примитивам.
- `crates/collab-engine` — модель комнаты поверх `Session`: команды движка идут тем же
  `Session::run`, что и в UI, с автором из JWT и без серверной истории undo.
- `crates/collab-client` — состояние клиента (opId, очередь, reconnect) без транспорта;
  `crates/collab-ws` — WebSocket-транспорт, который ведёт это состояние.
- `crates/collab-app` — сессия приложения: карта узлов, применение дельт, план локальной
  команды (дифф → примитивы), presence и участники; транспорт сокета остаётся в `collab-ws`.
- `apps/wordcraft-collab-server` — бинарь: `tokio` + `axum` WS, JWT, комнаты, снапшоты,
  commit; конфиг из env (`COLLAB_BIND`, `COLLAB_JWT_PUB`, `COLLAB_DATA_DIR`).
- Healthcheck `GET /healthz`; метрики `GET /metrics` (Prometheus-текст): комнаты,
  операции/с, отказы, задержка apply, размер журнала.
- Лимиты: документ ≤ 64 MiB, фрейм ≤ 1 MiB, участников ≤ 8, 200 операций/с на комнату,
  журнал ≤ 100 000 операций (дальше — принудительный снапшот).
- Логи без содержимого документа и токенов; в журнале — `sub` и `opId`.

## 10. Клиент

- **Feature flag:** `collab` в `Prefs` (default off) + env `WORDCRAFT_COLLAB=1` для
  headless; в web — `?collab=1`. Без флага ни одного сетевого вызова.
- Токен — из окружения (`WORDCRAFT_COLLAB_TOKEN`) или host-сообщения кабинета; в
  `Prefs` и URL он не попадает.
- Интеграция: перед командой `WordApp` запоминает `Document` (клонирование делит
  блоки через `Arc`), после — `collab-doc::diff` даёт примитивы (`replace_range`,
  `split_para`, `merge_para`, `insert_block`, `remove_block`, `move_block`,
  `permute`, `insert_row`, `remove_row`, `insert_column`, `remove_column`,
  `merge_cells`, `split_cells`). Перестановку соседних блоков diff узнаёт по
  указателям `Arc` (перемещение не создаёт новых блоков) и отдаёт одним
  `move_block` с двумя id; более широкую чистую перестановку того же отрезка —
  одним `permute` со списком id в новом порядке. Перестановку шире 64 блоков,
  которую примитив не назовёт, diff отклоняет, а не отправляет цепочкой
  текстовых замен. Смену уровня абзаца diff тоже не выражает (текст не
  меняется), поэтому `para.promote`/`demote` клиент отправляет командой, а
  сервер нормализует её в `set_para_level` (§4.2): реплики применяют уровни из
  дельты, а не повторяют команду, и undo возвращает прежние уровни одной
  транзакцией. Смену list-состояния diff тоже не выражает, поэтому
  `para.bullets`/`para.numbering` клиент отправляет командой, а сервер
  нормализует её в `set_para_list` (§4.2): реплики создают то же определение
  нумерации из `define`, а undo возвращает прежние ссылки и numbering id одной
  транзакцией. Так же `para.multilevel` и `para.restartNumbering` клиент
  отправляет командой, а сервер нормализует в `set_para_multilevel` /
  `set_para_restart_numbering`: реплики применяют уровни девятиуровневого
  списка или новый экземпляр с явным `start` из `define`.
  Дифф заходит в ячейки таблиц: печать в ячейке — `replace_range` по id абзаца
  ячейки, вставка/удаление строки — `insert_row`/`remove_row` с телом строки
  (обратная операция берёт его из дельты), вставка/удаление столбца —
  `insert_column`/`remove_column`, слияние и разбиение ячеек — `merge_cells`/
  `split_cells`. Эти четыре правки распознаются прогоном примитива таблицы на копии
  `Document` и сравнением с результатом; id ячеек не снимаются, а переиндексируются:
  ячейка, которую столбец сдвинул, переезжает вместе с поддеревом, ячейка, которую
  слияние поглотило, уходит в надгробия, а ячейка, в которой была каретка, сохраняет
  id. Неадресуемый диапазон (за границей сетки, с перевёрнутыми краями, начинающийся
  внутри вертикального объединения) отклоняется до изменения документа. Удаление
  столбца, слияние и разбиение обратимы: forward-операция снимает до правки то, что
  забирает (тела ячеек, сетку, исходные границы, id), и кладёт это в обратную
  операцию (`split_cells`/`merge_cells`/`insert_column` с полем `restore`). Обратная
  сверяет форму таблицы (span'ы всех строк, снятые после forward) до правки и при
  расхождении отвечает `undo-conflict`; восстановление id возвращает держателю
  каретки его ячейку. Размер `restore` ограничен (256 KiB, 16 384 id): регион больше
  не несёт обратной операции, и шаг, как раньше, `unsupported`. Форматирование,
  текстовое поле и несколько перемещений дифф не выражает — уходит `kind:"command"`
  с явным `selection`; такой шаг сервер исполняет тем же `Session::run`. Команда,
  меняющая форму таблицы, снимает id затронутых таблиц (надгробия) и выдаёт их
  заново: устаревший id ячейки получает `gone`, а не правит чужую ячейку.
- Чужие дельты применяются `collab-engine::apply_delta`: примитивы — напрямую в
  `Document` с пересчётом layout, команды — `Session::run_remote`, который не пишет шаг
  в локальный undo. Свои `applied` не применяются повторно (UI уже показал правку).
- Presence — из `sel`/`view`; 5–10 Гц, панель участников и чужие каретки рисуются в
  `ui-egui` (`collab.rs`).
- Viewer: команды, меняющие документ, отключены в UI до вызова движка, сервер
  дополнительно отвечает `forbidden`.
- `edit.undo`/`edit.redo` в совместной сессии уходят в комнату, а не в локальный
  snapshot-undo; одиночный режим не меняется.
- Track changes/комментарии: `author` = `sub` из JWT; `Session::author` выставляется
  сервером.

## 12. Безопасность

JWT только первым сообщением, не в URL; ключ из env, не в репозитории. Origin/`aud`
проверяются. Лимиты на размер фрейма, число комнат и участников. Снапшоты и журнал — на
диске с правами владельца процесса. В логи не попадают bytes документа, токены,
`payload` операций (только `opId`, `kind`, `version`, `sub`).

## 13. Открытые вопросы

1. ADR-0005: уточнить формулировку про `kept` (см. §4.6).
2. Подпись JWT: ES256 (по ADR-0008) — нужен ключ кабинета; до интеграции — тестовый ключ.
3. `commenter` в WordCraft: движок не различает «только комментарии»; сервер режет по
   allowlist `kind/target`, UI блокирует остальное.
4. Кто инициирует commit при выходе последнего участника, если он viewer (ADR-0009, п. 3).
5. Хранение: файловая система + `journal.jsonl` на комнату (v1) или Postgres (v2).
