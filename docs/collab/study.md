## 2. Модель документа

```rust
// crates/doc/src/lib.rs:99
pub struct Document {
    pub body: Blocks,                                 // Vec<Arc<Block>> (block.rs:12)
    pub last_section: SectionProps,
    pub parts: BTreeMap<u32, Part>,                   // headers/footers/notes/comments/text boxes
    pub styles: Arc<StyleSheet>,
    pub numbering: Arc<Numbering>,
    pub comments: BTreeMap<u32, Comment>,
    pub revisions: Vec<Revision>,
    pub settings: Settings, pub core: CoreProps, ...
    pub media: BTreeMap<String, Arc<Vec<u8>>>,
    pub passthrough: BTreeMap<String, Arc<Vec<u8>>>,  // части файла «как прочитано»
    ...
}
```

- `Block = Para(Paragraph) | Table(Table)` (`block.rs:7`), блоки всегда за `Arc`.
- `Paragraph { text: String, runs: Vec<Run>, props, mark, objects: Vec<InlineObject>, section, rev: u64 }`
  (`para.rs:28`): один ненормализованный `String` + список ранов, где `Run { len, props }`
  (`para/run.rs:33`) — ран адресует **длину в байтах**, а не свой текст.
- `Table { grid: Vec<f32>, rows: Vec<Row>, ... }`, `Row`/`Cell` (`table.rs:60`, `:37`, `:11`);
  ячейка держит `Blocks`, то есть таблицы вкладываются (лимиты `MAX_ROWS=32767`,
  `MAX_COLS=63`, `MAX_TABLE_DEPTH=18`).
- Истории: основная — `body`, вторичные — `parts: BTreeMap<u32, Part>`, `PartKind` =
  `Header | Footer | Footnote | Endnote | Comment | TextBox` (`parts.rs:26`).
- Владение: `Arc` + copy-on-write (`Arc::make_mut`), поэтому `Document::clone()` дешёвый —
  на этом стоит undo (см. §4). Стили и нумерация — общие `Arc`, копируются при правке.
- **Стабильных ID узлов нет.** Абзац/таблица/ран не имеют идентификатора; позиция — это
  `Pos { story: StoryRef, path: Path(Vec<u32>), off: usize }` (`position.rs:60`), где
  `Path` — индексы: `[block]` в истории, `[block,row,cell,block]` внутри ячейки, +3 индекса
  на уровень вложенности (`position.rs:15`).
- Есть **локальные** счётчики, не годичные для синхронизации: `Paragraph::rev` (номер из
  process-wide `AtomicU64`, `para/run.rs:26`, только для кэшей; не входит в `==` и в JSON),
  `Document::revisions: Vec<Revision>` с индексами, `free_id()` (`parts.rs:8`) — «на единицу
  больше максимального», общий аллокатор для частей, списков и комментариев.
- Атрибуция правок уже есть: `Revision { kind: Insert|Delete|Format, author, date, move_name }`
  (`review.rs:36`) и `Comment { author, initials, date, parent, resolved, part, durable_id }`
  (`review.rs:5`). Раны ссылаются на ревизии **индексом** в `Document::revisions`
  (`props/char_props.rs:353`: «Tracked insertion: index into `Document::revisions`»), при
  вставке фрагмента индексы пересчитываются (`edit.rs:1146`).

Вывод для collab: адресация «индекс-путь + байтовое смещение» корректна только при
последовательном применении правок в одном порядке; любые ID (части, комментарии, списки,
ревизии) выдаются из локального максимума и при параллельной работе двух клиентов совпадут.

## 3. Команды и мутации

- Единственная точка входа: `Session::run(&mut self, id: &str, params: &Value)`
  (`engine/src/session/run.rs:55`) — «the single entry point for the UI, CLI, MCP and control
  channel». UI, горячие клавиши, CLI, control-канал и MCP диспетчеризуются по строковому id.
- Реестр: `CommandSpec { id, label, location, shortcut, params, mutates, enabled, run }`
  (`engine/src/lib.rs:98`), полный реестр — `cmd::registry()` (`cmd.rs:62`) из 68 модулей.
  Я насчитал **656** `CommandSpec::new(...)` в `crates/engine/src/cmd`.
- Параметры — произвольный JSON; схема объявлена **строкой для агентов**
  (`params: "{"size": number}"`), машинной валидации нет. Тест
  `hostile_params_never_panic` прогоняет каждую команду с мусорными параметрами — то есть
  отказ на плохих данных — штатное поведение, а не авария.
- **Команды относительны выделения.** `text.insert` печатает в `self.sel`
  (`cmd/text/autoformat.rs:59`), `table.insertRowAbove` — строку у каретки. Позицию принимает
  только навигация, например `caret.set {"pos": Pos}` (`cmd/caret.rs:51`); `Pos` сериализуем.
  Значит «удалённая операция» = «поставить выделение и выполнить команду», а не «правка в
  точке X».
- Команды вызывают команды (вложенный `run`), ведут запись макросов, ловят панику и
  откатывают документ; неудачная команда оставляет документ как был (`session/run.rs:52-55`).
- **Журнала операций и обратных команд нет.** Ни `Command -> Inverse`, ни op-log: undo —
  это снапшоты (§4). Команды меняют модель напрямую через `doc.edit` (`crates/doc/src/edit.rs`:
  `split_paragraph`, `delete_range`, вставка фрагментов).
- Пересчёт layout не в командах, а в `Session::layout()` (`session/layout.rs:9`): кэш
  ищет запись по `self.rev`, режиму, ширине и т.п.; пересчитываются только изменившиеся
  абзацы (`crates/layout/src/cache.rs:10`: ключ включает `Paragraph::rev`).

## 4. Undo/redo

- Стек — в `Session` (`history`, `redo`), глобальный на документ/сессию, без разделения по
  пользователям.
- Элемент стека — **полный снапшот документа** плюс выделение, «ожидающее форматирование» и
  column-выделение: `Undo { label, doc, sel, pending, column }`, `checkpoint()`
  (`session/history.rs:7`). Снапшот дешёвый: блоки за `Arc`, копируется только изменённое.
- Глубина `MAX_UNDO = 500` (`doc_state.rs:179`), список для UI — 100
  (`UNDO_LIST_MAX`, `doc_state.rs:182`); вытесненные шаги считаются (`undo_evicted`).
- Типизация группируется (`typing_open`), drag — через `join_next_undo()`
  (`session/history.rs:37`), есть «пустая команда не создаёт шаг» (`unchanged()`, `run.rs:40`).
- Redo очищается на новом шаге. Отдельный JSON-снапшот сессии для восстановления/тестов —
  `session/snapshot.rs`.
- Следствие: **per-user undo в текущем виде невозможен** — стек не знает, чья это правка;
  для collab нужен либо журнал с автором, либо отдельные стеки на (пользователь, документ).

## 5. Сериализация и round-trip

- Dispatch по расширению: `engine/src/io.rs:11` (`OPEN_EXTS`) и `:31` (`SAVE_EXTS`);
  `.docx/.docm/.dotx/.dotm` — `crates/docx`, `.doc` — `crates/docbin` (только чтение),
  `.odt`, `.rtf`, `.md`, `.html`, `.tex`, `.txt` — `crates/formats`, `.json` — `serde` самого
  `Document`, `.pdf/.png` — экспорт.
- Round-trip держится на двух механизмах сохранения «того, что не смоделировано»:
  1. `Document::passthrough` — части пакета байт-в-байт (VBA, custom XML, встроенные шрифты,
     части объектов, `settings.xml` как прочитан; например `docx/src/read/embed.rs:138`,
     `docx/src/read/parts.rs:44`);
  2. `Document::kept` — исходный XML каждого абзаца/таблицы, который пишется обратно, пока
     `fingerprint` узла не изменился (`crates/doc/src/kept.rs:1-16`), лимит
     `MAX_KEPT_BYTES = 64 MiB` (`kept.rs:16`).
- Что **не** моделируется и потому живёт только «как прочитано»: неизвестные элементы и
  атрибуты, VBA-проект (неправильно: сохраняется как opaque-часть), подписи, часть OLE,
  произвольные XML-части; в `docs/file-format-parity.md` и `docs/gaps.md` — известные
  расхождения. Макросы и шифрование: `.docx`/`.odt` с паролем читаются (agile/standard),
  VBA сохраняется байт-в-байт.
- «Прочитать → записать без правок»: изменённые абзацы пишутся из модели, неизменённые — из
  `kept`; неизвестные части — из `passthrough`. Практически это самый строгий round-trip из
  пяти проектов, но он **привязан к отпечатку содержимого**: любая правка абзаца выбрасывает
  его исходный XML, а вместе с ним и то, что модель не поняла.
- Важно для commit: сохранение — это **сборка всего пакета** (`save_bytes`/`save_path`,
  `io.rs:441`), а не патч. Диффа между двумя версиями на уровне модели нет (есть
  `compare.rs` для сравнения документов, но не для merge).

## 6. Структурные правки и их цена

| Операция | Что ломается при конкурентной правке | Цена пересчёта |
|---|---|---|
| вставка/удаление абзаца | `Path` — индексы: вставка выше сдвигает все последующие пути; у удалённого абзаца нет ID, «тот же» абзац у другого клиента уже другой | пересчёт затронутых абзацев + поток страниц; документировано 1.4 мс на правку для 188-страничного документа (`docs/architecture.md:50`, замер 2026-10-06; мной не перемерялось) |
| таблица: строка/столбец/ячейка | в `Path` зашиты `row`/`cell` индексы; вставка строки сдвигает ячейки; `grid: Vec<f32>` и ширины меняются целой таблицей | пересчёт таблицы и её страниц (`layout/src/table*.rs`) |
| стили/нумерация | `styles`/`numbering` — общие `Arc`; правка копирует весь лист; новые id из `free_id()` совпадут у двух клиентов; чужие ссылки на стиль по имени | пересчёт всех абзацев, использующих стиль |
| сноски/комментарии/track changes | `parts: BTreeMap<u32, Part>` — id из `free_id()`; `Comment.part` — id истории; раны ссылаются на ревизии индексом в `Vec<Revision>` | локально, но ссылки индексами требуют пересчёта при вставке/удалении ревизии |
| вложенные объекты (картинки, фигуры, уравнения, текстовые боксы) | `media: BTreeMap<String, Arc<Vec<u8>>>` — ключи-строки; текстовый бокс — отдельная `Part` с id; OLE/графика — непрозрачные `Arc` | растеризация медиа и layout боксов |

## 7. Существующие хуки для collab

Есть:
- `Session` как единственная точка мутаций — идеальная граница для интерсептора;
- `dirty`, `document_id` (уникальный id открытого документа, `session.rs:127`), path;
- control-канал: JSON-строки по TCP на `127.0.0.1`, ключ окна, методы `engine.execute`,
  `document.inspect`, `ui.*` (`docs/control-protocol.md`) — готовый внешний «пульт»;
- MCP-сервер (`crates/mcp`): те же команды как тулы, headless-режим — можно поднять
  вторую сессию в процессе без GUI;
- headless-инструменты для тестов: `wordcraft-cli run --script`, `ui_shot`, `perf_probe`;
- recovery/autosave (`docs/recovery.md`) — уже есть понятие «черновик на диске».

Нет и придётся добавить:
- стабильные ID узлов/абзацев/ранов и маппинг «модель → ID» на время сессии;
- журнал применённых операций (сейчас есть только снапшоты undo);
- приём и применение чужих операций (сейчас `run` относителен выделения и локального
  состояния сессии);
- уведомления об изменениях для внешнего наблюдателя (отдельной шины событий нет: UI просто
  вызывает `layout()` после команды);
- сетевого кода нет вообще: в зависимостях нет `tokio`/`tungstenite`/`ws`
  (проверено `grep` по `Cargo.toml`).

## 8. Производительность

- Пересчёт: инкрементальный layout с пер-абзацным кэшем по `rev`; документировано
  **1.4 мс на правку в документе на 188 страниц** (`docs/architecture.md:50`). Мной не
  перемерялось (нет toolchain).
- Undo: снапшот на каждую мутирующую команду, но клонирование `Document` — это клонирование
  `Arc`-ов; цена растёт на изменённых блоках и на смене стилей/нумерации.
- Размеры документов не измерял. Из кода: лимиты `MAX_KEPT_BYTES = 64 MiB`,
  `MAX_ROWS = 32 767`, `MAX_COLS = 63`, `MAX_TABLE_DEPTH = 18`, `MAX_TYPED_PARAGRAPHS = 10 000`
  (массовая вставка абзацев одной командой) — то есть документ на 100+ страниц штатный,
  а «весь документ на каждое нажатие» — заведомо неверная стратегия.
- WASM: `apps/wordcraft-web` собирается под `wasm32-unknown-unknown`, 374 места с
  `cfg(target_arch = "wasm32")`. Потоков в браузере нет: `rayon` используется только в
  нативном рендере (`render/src/context_pool.rs`), в вебе — WebGPU/WebGL2. Сети в вебе нет
  (нет TCP control-канала); WebSocket-клиента тоже нет — его придётся добавлять
  (`web-sys`/`gloo-net`), и он должен работать без `SharedArrayBuffer` и без потоков.
  Размер бандла не измерял.

## 9. Три варианта протокола (кратко)

| Вариант | Суть | Плюсы | Минусы | Риск |
|---|---|---|---|---|
| A | Единица операции = команда `Session::run(id, params)`; сервер — последовательная очередь, позиция передаётся явным `Pos`, при конфликте — отказ + полный снапшот документа | ничего не меняет в модели; 656 команд уже есть; MCP/CLI/control уже так работают | команды относительны выделения; `Pos`-индексы устаревают; нет инверсий для перебазировки; при отказе — передача целого документа | средний: работает на 2 клиентах «по очереди», ломается на параллельной типизации |
| B | Нормализованный набор операций над моделью (≈20 примитивов: `insert_text`, `delete_range`, `split_para`, `set_run_props`, `insert_block`, `insert_row`, `set_style`…), клиент компилирует команды в них, сервер транслирует индекс-пути (OT по путям) и рассылает подтверждённые операции | узкая поверхность, стабильная семантика, проверяемо headless, сохраняет round-trip: в модель пишется тот же `doc.edit` | нужен маппинг «команда → примитивы» для 656 команд и трансформация индексов; стили/ревизии надо адресовать иначе (ID или версии) | низкий-средний: объём работы на клиенте, но архитектура совпадает с моделью |
| C | CRDT: последовательность символов и блоков с уникальными ID (Yjs/Peritext-подобно), сходимость без серверной трансформации | offline и параллельная типизация «из коробки», нет отказов | в модели нет ID, `String`+`runs` не CRDT; стили/нумерация/ревизии — глобальные структуры; «не тащить тяжёлый CRDT-стек» противоречит Rust/WASM-бюджету | высокий: переписывание модели ввода текста и всех команд |

Рекомендация и обоснование — в `options.md`.

## 10. Риски и открытые вопросы

1. **Нет ID** — самый дорогой пункт: нужен слой «стабильные ID ↔ индекс-путь» на время
   сессии (join-time assignment) либо полный переход модели на ID.
2. **`free_id()` и параллельность**: части/комментарии/списки получат одинаковые id у двух
   клиентов; нужен серверный аллокатор диапазонов или префикс клиента.
3. **Ревизии индексные**: `CharProps.ins/del` — индексы в `Vec<Revision>`; при параллельных
   правках с track changes индексы разъедутся, нужен маппинг.
4. **`kept`/`passthrough`**: правка абзаца выбрасывает исходный XML → часть неизвестного
   содержимого теряется; серверный commit должен собирать файл на одной модели, а не
   склеивать `kept` от разных клиентов.
5. **Undo глобальный и без автора** — per-user undo потребует журнала с автором и
   собственного стека на пользователя.
6. **Команды относительны каретки** — удалённое применение требует и выделения, а оно у
   каждого клиента своё; в протоколе нужен явный «курсор операции», а не «мой курсор».
7. **Нет сети в вебе** — WebSocket-клиент и реконнект писать с нуля; в десктопе — тоже нет
   сетевого стека.
8. Не измерено: размер типичного/максимального документа, время полного layout, размер
   WASM-бандла, стоимость снапшота на 100+ страницах (всё — после появления toolchain в
   фазе реализации).
