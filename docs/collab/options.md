# Options: WordCraft — механизм совместного редактирования

- Проект: `wordcraft`
- Upstream: `https://github.com/storytold/wordcraft`, коммит `2a0a20ae`
- Дата: 2026-11-06, автор `wordcraft/envoy`
- Основание: `study.md` в этом же каталоге

Задача: выбрать **механизм**, а не «оттенок» одного и того же. Все три варианта
укладываются в общий для пяти проектов конверт (WS + JSON, JWT, версия документа,
`opId`, `author`), различается то, **что именно** летит в конверте и **кто разрешает
конфликты**.

Ключевые факты из `study.md`, которые отсекают варианты:

1. Стабильных ID узлов нет; адресация — `(story, Path(Vec<u32>), off)` (`doc/src/position.rs:15,60`).
2. Правки идут только через `Session::run(id, params)`, и команды относительны выделения
   (`engine/src/session/run.rs:55`, `cmd/text/autoformat.rs:59`); журнала операций и
   инверсий нет.
3. Undo — снапшот всего `Document` на команду (`session/history.rs:7`), глобальный, без автора.
4. Модель держится на `Arc`-блоках (`doc/src/block.rs:12`) — дешёвые клоны и дешёвое
   сравнение «что изменилось» по указателю.
5. Round-trip держится на `kept` (исходный XML абзаца) и `passthrough` (части пакета);
   любая правка абзаца выбрасывает его `kept` (`doc/src/kept.rs:1`).
6. Сети (WS/TCP-клиента) в кодовой базе нет; в вебе нет потоков (`apps/wordcraft-web`).

## Вариант A — команда как единица операции

**Механизм.** Клиент выполняет `Session::run` локально и отправляет на сервер
`{id: "text.insert", params: {...}}` вместе с явным `Pos`/выделением, к которому команда
относилась. Сервер держит единственную авторитетную `Session`, применяет команды строго по
очереди, при несовпадении версии/невозможности применить — отказывает и присылает полный
снапшот документа (`.json` модели или `.docx`).

**Что уже есть:** 656 команд, реестр, JSON-параметры, откат при ошибке, защита от паники,
control-канал и MCP уже работают ровно так.

| Плюсы | Минусы |
|---|---|
| Ноль изменений в модели и в 656 командах | Команда — не позиционная операция: `text.insert` печатает в каретке сессии, серверу придётся подменять выделение перед каждым вызовом |
| Один и тот же код на клиенте и сервере (headless-сессия) | Нет инверсий → нельзя перебазировать чужую команду, только отклонить |
| Быстрый старт, легко показать в демо | Отказ = полный документ по сети; на 100+ страницах это мегабайты на каждый конфликт |
| Параметры уже JSON и проверены `hostile_params_never_panic` | Составные команды (вставка 10 000 абзацев, paste) — атомарный «монолит», трансформации не поддаётся |
| | Не даёт per-user undo: undo-снапшот сервера общий |
| | Стили/нумерация/ревизии меняются глобально — «команда одного клиента» меняет чужое состояние |

Оценка: **самый дешёвый вход, самый хрупкий результат.** Годится для «двух редакторов по
очереди», не годится для критериев 2–4 из AGENDA (2–5 участников, per-user undo, без
пересылки всего документа).

## Вариант B — нормализованные операции над моделью + серверная трансформация путей

**Механизм.** Вводится узкий набор примитивов (≈20), каждый — чистая функция над `Document`,
реализованная через существующий `doc::edit`:

```
insert_text(story, path, off, text, props?)
delete_range(story, path, off, len)
split_para(story, path, off)            merge_para(story, path)
set_run_props(story, path, off, len, patch)
insert_block(story, path, index, block) remove_block(story, path, index)
move_block(story, from, to)
insert_row(table_path, index, row?)     remove_row(table_path, index)
insert_col/remove_col(table_path, index)
set_para_props(...)  set_table_props(...)  set_section_props(...)
set_style(name, patch)  set_numbering(id, patch)
add_comment(anchor, text)  set_revision(...)  set_field(...)
```

Клиент после каждой локальной команды **выводит** изменившиеся примитивы: `Arc::ptr_eq`
даёт список изменённых блоков бесплатно, внутри изменённого абзаца — минимальный
текстовый дифф по байтовым смещениям. Операция уходит на сервер с `baseVersion` и
`author`. Сервер — единственный писатель: присваивает `version`, транслирует пути
(вставка/удаление блока или строки сдвигает индексы в чужих операциях, находящихся «в
полёте»), применяет, рассылает подтверждённую операцию с уже трансформированными путями.
Отказ возможен только там, где операция семантически невозможна (удалённый абзац,
запрет редактирования), и тогда — ресинк **одной истории**, а не всего документа.

**ID.** Сервер при join выдаёт клиенту сессионный префикс; `free_id()` заменяется на
«серверный аллокатор диапазонов» для частей/комментариев/списков; к индекс-путям
добавляется карта `ID ↔ path`, которую сервер обновляет при каждой структурной операции.
Это ровно то, что просит измерение 2 (`protocol/id-strategy`).

| Плюсы | Минусы |
|---|---|
| Совпадает с моделью: примитивы — это то, что уже делает `doc::edit`, round-trip не страдает | Нужен слой «команда → примитивы»; для 656 команд он не пишется вручную целиком — начинаем с 20 примитивов и покрываем команды по мере надобности |
| Трансляция нужна только для индексов блоков/строк/ячеек, не для символов → OT-код маленький и тестируемый | Стили/нумерация/ревизии всё равно глобальны: их правки — «сериализуемые» операции с версией, а не слияние |
| Никакой пересылки всего документа на нажатие: операция — десятки байт | Нужна аккуратность с `kept`: commit собирает файл из авторитетной модели, `kept` берётся только для нетронутых узлов |
| Per-user undo: журнал операций с `author` и группировкой по `undoLabel` даёт стек на пользователя | Появляется второй «писатель» модели — сервер; нужно синхронизировать версию модели в `Session` (сервер авторитетен, клиент догоняет) |
| Годится всем пяти проектам: примитивы — это «словарь моделей», конверт общий | Требует головной работы: ID, журнал, трансформация — оценочно недели, не дни |
| Headless-тестируемо: `wordcraft-cli run --script` + две сессии в одном процессе, без GUI | |

Оценка: **средняя цена, попадает во все 7 критериев AGENDA.** Это рекомендуемый вариант.

## Вариант C — CRDT на дереве документа

**Механизм.** Каждый символ и каждый блок получают уникальные ID (Lamport/клиентский
префикс); текст абзаца — sequence CRDT (RGA/YATA, идея Peritext), список блоков —
movable-list CRDT, атрибуты — LWW-регистры. Сервер не трансформирует ничего: он хранит
операции и периодически компактит.

| Плюсы | Минусы |
|---|---|
| Сходимость без отказов, offline «из коробки» | Модели нужны ID **везде**: `Paragraph.text: String` + `Run{len}` (`doc/src/para.rs:28`, `para/run.rs:33`) — это не CRDT; переписывание ввода текста, ранов, `Pos` и всех команд |
| Естественный per-user undo (свои операции) | Глобальные структуры (`styles`, `numbering`, `revisions: Vec<Revision>` с индексными ссылками из `CharProps.ins/del`, `parts: BTreeMap<u32, Part>`) в CRDT не ложатся; их всё равно придётся сериализовать |
| Не нужен серверный OT-код | «Не тащить тяжёлый CRDT-стек» (AGENDA, критерий 6): `yrs`/`diamond-types` — это ещё и wasm-совместимость, размер бандла, чужая модель документа |
| | Round-trip под угрозой: `kept` привязан к отпечатку абзаца; CRDT-перестройка абзаца постоянно меняет отпечаток → теряется всё, что модель не понимает |
| | 656 команд пишут в модель напрямую — каждая станет источником CRDT-операций, которые надо вывести из `String`-мутации |
| | Тестирование сходимости пяти разных моделей — отдельный большой трек |

Оценка: **высокий риск, не в бюджете Phase 0.** Имеет смысл только если появится
требование offline-first, которого в TASK.md нет.

## Рекомендация: **B**

Почему именно B для WordCraft:

1. **Модель уже почти позиционная.** `doc::edit` оперирует `Pos`/`Path` и умеет
   `split_paragraph`, `delete_range`, вставку `Fragment` — примитивы B — это тонкая обёртка
   над готовым кодом, а не новая модель документа. A этого не использует (команды
   относительны выделения), C требует переписать `String`+`Run` в CRDT.
2. **Трансформация нужна только для индексов.** Текст адресуется `(path, off)`, поэтому
   конфликт «двое печатают в одном абзаце» решается сдвигом `off`, а не слиянием
   последовательностей. Это десятки строк OT-логики вместо CRDT-движка.
3. **`Arc`-дифф даёт бесплатный детектор изменений.** `Arc::ptr_eq` по `body`/`parts` после
   `Session::run` точно говорит, какие блоки изменились; внутри абзаца — минимальный
   текстовый дифф. Клиенту не нужно переписывать 656 команд, чтобы начать.
4. **Round-trip остаётся нашим.** Commit собирает `.docx` серверной моделью
   (`io::save_bytes`), `kept`/`passthrough` живут на авторитетной копии — то, что модель не
   понимает, не теряется из-за чужого клиента.
5. **Ложится на общий конверт пяти проектов.** `insert_text/delete_range/insert_block/…` —
   это словарь, который есть у GridCraft (ячейки/строки), DeckCraft (слайды/фигуры),
   PdfCraft (страницы/аннотации), CADCraft (слои/примитивы). Один транспорт, один
   `opId`/`version`/`author`, разные наборы примитивов.

Что B **не** решает и требует отдельных решений (измерения 2, 3, 6, 8, 10):

- **ID (2):** серверные диапазоны для `free_id()` + сессионная карта `ID ↔ path`;
  полноценные ID узлов — отдельным ADR, только если понадобится offline.
- **Порядок (3):** серверный монотонный `version` + `opId`; Lamport не нужен, один писатель.
- **Presence (6):** отдельный топик того же WS, 5–10 Гц, без backpressure на документ.
- **Auth (8):** JWT кабинета, lease «одна сессия на документ на пользователя», отзыв — по
  `exp`+`jti` в журнале.
- **Commit (9):** сервер собирает файл из авторитетной модели, `409` при несовпадении
  `baseVersion` на момент commit; callback в кабинет — вне WordCraft.
- **Undo/offline (10):** журнал операций с `author` и `undoLabel`; offline-очередь —
  отдельная фаза, B её не запрещает (операции идемпотентны по `opId`).
